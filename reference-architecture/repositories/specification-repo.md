# The Product Specification Repository

One repository per product holds the product's entire canonical state:
the PP `.product/` tree exactly as bound by
[PP-0002 §7](../../pp/PP-0002-core-concepts.md#7-git-storage-binding),
plus a small set of RA v1 additions that live *outside* `.product/`
because the protocol does not define them. For `aurora-books` the repo
is `aurora-books-product`.

This repo is the runtime's database. The
[scheduler](../runtime/kubernetes.md) reconciles against it, every
[Claude Code session](../runtime/claude-code-sessions.md) reads its
context from it and writes its results back to it, and
[Linear](../runtime/linear-integration.md) and the vault are projections
of it. If this repo is intact, the whole system can be rebuilt; nothing
elsewhere is state.

## Layout

```
aurora-books-product/
├── .product/                       # PP-0002 §7 Git binding — protocol-defined
│   ├── product.yaml                # the Product object
│   ├── brain/                      # ProductBrain (PP-0003 §6)
│   │   ├── brain.yaml
│   │   ├── knowledge/              # Knowledge objects
│   │   └── decisions/              # Decision records (append-only)
│   ├── specification/              # Goal, Capability, Specification, Feature, Story
│   ├── constitution/               # Constitution objects
│   ├── tasks/                      # Task objects — the Task Graph (PP-0006 §4)
│   │   └── artifacts/              # Artifact records (PP-0007 §6)
│   ├── workers/                    # Worker declarations
│   ├── evaluation/
│   │   ├── evaluators/             # Evaluator declarations (PP-0008 §5)
│   │   ├── golden/                 # GoldenTest objects
│   │   ├── gates/                  # QualityGate definitions (PP-0008 §9)
│   │   └── runs/                   # Evaluation records (append-only)
│   ├── deployments/                # Deployment records + environment declarations
│   ├── observations/               # Observation records (append-only)
│   └── issues/                     # Issue objects
├── prototypes/                     # RA addition: HTML prototypes per Story/Feature
│   ├── guest-checkout.html
│   └── recs-shelf.html
├── schemas/                        # RA addition: product-local x- extension schemas
│   └── x-aurora-merch-rule.schema.json
├── reports/                        # RA addition: GENERATED — never hand-edited
│   ├── traceability.md             # Goal → Story → Task → Evaluation matrix
│   ├── audit.md                    # constitution-audit summaries
│   └── velocity.md                 # attempts, cycle time, cost per task
├── datasets/                       # RA addition: reference data for golden tests
│   └── checkout-carts-v3/          # versioned per PP-0008 §6.3
├── .github/
│   └── workflows/                  # validate, evaluate, approval, sync (see below)
├── CLAUDE.md                       # per-product agent context (see claude-md.md)
└── pp.yaml                         # self-binding: product id (same format as
                                    # engineering repos, spec repo points at itself)
```

Rules RA v1 adds on top of the binding:

- Nothing outside the list above is committed to this repo. In
  particular: no application code, no node_modules-style vendoring, no
  binary artifact payloads — payloads live in the evidence store or
  engineering repos and are referenced by digest (PP-0002 §7).
- `reports/` is regenerated by CI on every merge to `main`; a PR that
  hand-edits `reports/` fails validation.
- `datasets/` directories are versioned by suffix (`-v3`) and treated
  as frozen once referenced by an approved GoldenTest, mirroring
  PP-0008 §6.3 dataset pinning.

| --- | --- | --- |
| `.product/product.yaml` | Humans, Architect (proposals) | Rarely changes; environment list changes reviewed by humans |

| `.product/constitution/` | Product Writer, Architect (proposals) | Amendments are new versions in `draft`; approval human-only |

| `.product/evaluation/runs/` | Evaluation Manager | Append-only; evidence by CI artifact digest |

| `reports/` | CI only | Generated |
| `datasets/` | QA Engineer, Evaluation Manager | Frozen once referenced by approved GoldenTests |
| `CLAUDE.md` | Librarian (proposals), humans | Kept lean per [claude-md.md](claude-md.md) |

## PR conventions

All writes land through PRs on `task/<task-id>` (or
`proposal/<object-id>` for governed-object proposals raised outside a
task). Three PR shapes cover everything:

### 1. Governed-object proposals — merge *is* the Decision

A change to anything governed (Goal, Capability, Specification,
Feature, Story, GoldenTest, Constitution) is a PR that adds or bumps
the object at a new `metadata.version` with `lifecycle: proposed`.

- CODEOWNERS routes governed paths to humans; only a human review can
  satisfy the required approval.
- The PR body is the approval-queue entry (PP-0010 §7): rendered diff
  against the prior approved version, provenance links, affected
  objects. The Product Writer generates this; the
  [vault](../knowledge/README.md) surfaces the same queue for humans.
- **The human's approving review + merge is the approval event.** The
  merge triggers the `approval` workflow, which flips
  `metadata.lifecycle` to `approved` and commits the corresponding
  `Decision` record into `.product/brain/decisions/` under the
  approver's identity, referencing the exact object version
  (PP-0002 §6.2). Agents never perform this transition; the workflow
  runs only on human-approved merges to protected `main`, and the
  Decision commit is signed by the workflow's attestation identity
  with the approver recorded as the deciding actor. See
  [GitHub integration](../runtime/github-integration.md#governed-object-approval-flow).

### 2. Task-state and record PRs

The runtime (via `pp-spec`) batches status transitions, Artifact
records, Evaluation records, and Observations into small commits on
`main` through a fast-path merge queue — these are `status`/record
writes the protocol assigns to the managing implementation
(PP-0002 §3), so they are not human-reviewed, but they are still
schema-validated and append-only-checked before merge.

### 3. Planning PRs

The Planner's task-graph changes (new Tasks, `dependsOn` rewires,
priorities, replans) merge as reviewed-by-check PRs: no human required,
but validation must prove acyclicity (PP-0006 §4), source lifecycle
(only `approved` Stories/Features, non-`open` Issues — PP-0006 §2.1),
and completion contracts before `ready` (PP-0006 §5.5).

Commit conventions in all three shapes: one object concern per commit,
`PP-Task: <task-id>` trailer where the change is task-driven, no force
pushes, no history rewrites (append-only kinds rely on Git history as
the audit trail).

## CI in the spec repo

Mirroring this repository's own
[`scripts/validate-examples.mjs`](../../scripts/validate-examples.mjs),
the spec repo validates itself on every PR and push:

| Workflow | Trigger | Does |
| --- | --- | --- |
| `validate.yml` | every PR | Schema-validate every object against the [PP schemas](../../schemas/README.md) and `schemas/` extensions; reject unknown top-level fields; check ref integrity (no dangling refs, PP-0002 §5); task-graph acyclicity; lifecycle legality (no skipped states, no edits to `approved` versions or append-only records); completion contract present on `ready` tasks |
| `traceability.yml` | merge to `main` | Regenerate `reports/traceability.md` (Goal → Capability → Feature → Story → Task → Artifact → Evaluation), `reports/velocity.md`, prototype index |
| `evaluate.yml` | task submission events | Dispatches golden suites in the owning engineering repos; collects results for the Evaluation Manager ([evaluation](../evaluation.md)) |
| `approval.yml` | merge of governed-object PRs | Lifecycle flip + Decision record, as above |
| `sync-linear.yml` / `sync-vault.yml` | merge to `main` | Push projections ([Linear](../runtime/linear-integration.md), vault views) |

A red `validate.yml` is a hard stop: it is a required check on `main`,
so no object — human- or agent-authored — enters the canonical tree
malformed.

## Prototypes

`prototypes/` holds self-contained HTML files (inline CSS/JS, no build
step) produced by the Frontend Engineer during specification: one
clickable sketch per Story or Feature under discussion, named after
its object id (`guest-checkout.html` ↔ `feat-guest-checkout`). The
[e-commerce example](../../examples/ecommerce/prototypes/guest-checkout.html)
shows the shape.

Serving for review:

- `traceability.yml` publishes `prototypes/` to GitHub Pages on merge,
  so every prototype has a stable review URL.
- On proposal PRs that touch a prototype, a preview deployment comment
  links the PR's version, and the approval-queue entry embeds it — the
  human approving a Story sees the prototype it describes.
- Once the Story is approved, the prototype is frozen alongside it; a
  revised Story version gets a revised prototype. Prototypes are
  reference material for Workers (linked from `Task.spec.context.notes`),
  never the implementation.

## Relationship to engineering repos

The spec repo points at its engineering repos in
`Product.spec.repositories`; each engineering repo points back with a
root [`pp.yaml`](engineering-repos.md#binding-a-repo-to-its-product).
Code never crosses the boundary — only Artifact records (commit/PR
digests) flow in, and only Task context flows out.
